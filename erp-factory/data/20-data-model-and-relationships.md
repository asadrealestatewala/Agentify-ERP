# 20 — Data model, conventions & relationships

Source: `server/src/schema.js` (65 `CREATE TABLE`), `db.js migrate()`, `supabase/schema.sql` (56-table Postgres mirror), `ARCHITECTURE.md §1, 8, 15–22`.

## Conventions (apply to every table in every ERP)

| Convention | Rule |
|---|---|
| Primary key | `id INTEGER PRIMARY KEY` (SQLite rowid alias); Postgres mirror: `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| Human number | separate unique `*_no` / `*_code` text column from `nextNo()` — never expose `id` as the business number |
| Timestamps | `created_at TEXT NOT NULL` (tenant-local `YYYY-MM-DD HH:MM:SS`), `updated_at TEXT`, optional `*_by` user id. Dates `YYYY-MM-DD` |
| Money | `INTEGER` whole currency units; quantities `REAL`; rate `REAL` |
| Flags | `INTEGER NOT NULL DEFAULT 0/1`; `active`, `published`, `is_demo`, `portal_visible`, `own_scope`… |
| Status | `TEXT NOT NULL DEFAULT '<first-state>'` (state machine documented in code) — no status tables, **except** configurable ones in `lookups` |
| Configurable lists | one `lookups(type, value, color, meta JSON, sort_order, active)` table for every dropdown (lead_stage, lead_source, property_type, amenity, payment_method, expense_category, vendor_category, department, designation, leave_type, document_category, construction_activity, asset_category, employment_type…). Colours and behaviour flags live in `meta`/`color` |
| Custom fields | `custom_fields(entity, key, label, type, options, required, sort_order)` + `custom TEXT JSON` column on the entity (contacts) — extra fields without schema change |
| JSON columns | `tags`, `features`, `amenities`, `videos`, `boq`, `sections`, `platforms`, `posted`, `asset_info`, `custom`, `rules`, `tiers` as TEXT; parsed by `jparse` |
| Polymorphic links | `(entity_type, entity_id)` pairs for `documents`, `media`, `notes`, `tasks`, `activities` — one table serves every entity; indexed on the pair |
| Soft vs hard delete | financial/legal records: **never deleted** (void/cancel with reason + reversing entry). Config & drafts: hard delete guarded by FK errors → "in use" message |
| Demo data | `is_demo` column on seeded business tables; one switch to purge |
| Indexes | add for every FK used in filters/joins and every `(status, id)` hot list; **partial unique indexes** for optional unique business codes |
| Migrations | additive only (`ALTER TABLE ADD COLUMN` with default), idempotent, run at every open; destructive table rebuild only inside a guarded transaction with `foreign_keys=OFF` (done once for `sales.property_id` nullable) |
| Cascade | `ON DELETE CASCADE` only for owned children (installments, dev_items, dev_updates, journal_lines, role_permissions, tender_bids, work_task_updates, asset_history, auth tokens); never for business parties |

## Invariants the tests assert (copy as acceptance criteria)

1. `SUM(journal_lines.debit) = SUM(journal_lines.credit)` globally and per journal.
2. Receivable control account (1300) = Σ `(net_price − paid_amount)` of confirmed sales.
3. For each confirmed sale: Σ `installments.paid` = `sales.paid_amount` = Σ valid `receipt_sales.amount`; Σ `installments.amount` = `net_price`.
4. Vendor payable (2100 by vendor) = Σ `(amount − paid_amount)` of approved/partial vouchers.
5. A void/cancel posts a reversing journal (`reversal_of`) and cannot be applied twice.
6. Overpayment is accepted only when explicitly flagged and goes to 2200 Customer Advances.
7. A sold property cannot be sold again; reserved only for the reserving contact.
8. Agent token never returns another agent's contact/sale/commission; customer token returns only its own contact's records; vendor only its own.
9. A token issued by tenant A is rejected on tenant B.

## Deriving "derived" data (no stored duplicates)

Dashboards, goals/points/streaks, schedule % and forecast, customer 360 next-best-action, today feed, project income/expense/receivable, vendor billed/released/remaining (cross-checked with `books_in_sync`), attendance %, plot map are all **queries over primary tables**. If a screen needs a stored cache for speed (paid_amount), tests must prove it reconciles.

## Postgres mirror (`supabase/schema.sql`)

Generated from the SQLite schema: `BIGINT` everywhere for money/ids/flags (booleans stay 0/1 integers, timestamps stay PKT text exactly as the app writes them), identity PKs, `IF NOT EXISTS` (idempotent), RLS enabled. **Status: partial and already stale.** It has 56 tables; the live schema has 65. Missing from the mirror (checked by diffing `CREATE TABLE` names): `auth_tokens, verify_tokens, tenders, tender_bids, payment_claims, payment_feed, bot_kb, bot_chats, site_page_versions` — i.e. every table added after the mirror was generated. Regenerate it from `schema.js` (and add a CI check that the table-name sets match) before relying on it. Runtime is still SQLite because every query would have to become async. Treat the mirror as a migration target and a Supabase-hosted read/sync surface (see `sync/30-sync-and-integration-patterns.md`); do not claim "runs on Postgres" for a delivered ERP.
